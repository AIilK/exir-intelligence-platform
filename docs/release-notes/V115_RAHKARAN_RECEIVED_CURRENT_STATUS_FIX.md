# V115 — اصلاح وضعیت فعلی چک‌های دریافتی راهکاران

## مسئله
لیست داشبورد از `ReceivableNote.State IN (1,2)` استفاده می‌کرد. فایل گزارش واقعی راهکاران نشان می‌دهد «وضعیت فعلی» عملیاتی است و لزوماً با State هدر یکی نیست.

کنترل فایل ارسالی `ListData (71)(1).xlsx`:

- کل چک باز بر اساس **وضعیت فعلی**: **796 فقره**
- مبلغ کل باز: **75,828,510,498 تومان**
- نزد بانک: 720 فقره / 64,250,619,498 تومان
- نزد صندوق: 66 فقره / 11,065,678,000 تومان
- نزد مأمور وصول: 9 فقره / 462,213,000 تومان
- در انتظار واگذاری به مأمور وصول: 1 فقره / 50,000,000 تومان

در V114 داشبورد 812 فقره / 76,846,527,598 تومان نشان می‌داد؛ بنابراین State هدر به تنهایی مبنای صحیح «وضعیت فعلی» نبود.

## اصلاح V115

1. وضعیت جاری راهکاران از **آخرین ReceivableNoteTransaction مثبت و تأییدشده** گرفته می‌شود.
2. اگر تراکنش وضعیت وجود نداشته باشد، فقط آن‌وقت `ReceivableNote.State` fallback است.
3. وضعیت‌های قطعی وصول/واخواست/واگذاری به غیر/استرداد از سبد باز حذف می‌شوند.
4. وضعیت‌های مثبت عملیاتی ناشناخته به‌صورت خودکار حذف نمی‌شوند؛ بنابراین وضعیت‌های مأمور وصول/در انتظار مأمور وصول که الزاماً State 1/2 نیستند می‌توانند داخل سبد باز بمانند.
5. همین منطق به چک و سررسید، Customer open cheques، Cheque Risk، Cash Flow forecast و تمرکز سررسیدها وصل شده است.

## کنترل جدید
Endpoint جدید:

`GET /api/v1/treasury/cheques/received/current-state-quality`

خروجی، عدد Legacy و Business Current را کنار هم نشان می‌دهد و تک‌تک mismatchها را با شماره سریال، مبلغ، MasterState و EffectiveState برمی‌گرداند.

SQL read-only کنترل نیز در:

`diagnostics/V115_Received_Cheques_Current_State_Reconciliation.sql`

قرار دارد.

> نکته: عدد نهایی روی SQL شرکت باید بعد از اجرای V115 کنترل شود؛ محیط ساخت به SQL داخلی شرکت دسترسی ندارد. هدف این نسخه حذف حدس State=1/2 و هم‌راستا شدن با منطق «وضعیت فعلی» راهکاران است.
