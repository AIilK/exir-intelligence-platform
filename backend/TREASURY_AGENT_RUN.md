# راه‌اندازی Agent خزانه

## 1. ساخت محیط با Python 3.12 در ویندوز

در پوشه `backend` اجرا کنید:

```bat
py -3.12 -m venv .venv312
.venv312\Scripts\activate
python --version
python -m pip install --upgrade pip
pip install -r requirements-treasury.txt
```

خروجی `python --version` باید با `Python 3.12` شروع شود. اگر محیط قدیمی پروژه با
Python 3.11 ساخته شده، همان محیط را فعال نکنید؛ خطای `KeyError: ~TContext` هنگام
import نسخه جدید Agents SDK در آن محیط مشاهده شده است.

برای اتصال SQL Server باید **ODBC Driver 17 for SQL Server** روی ویندوز نصب باشد.

## 2. تنظیم فایل `.env`

از `.env.example` یک کپی با نام `.env` بسازید و این مقادیر را تکمیل کنید:

```env
SQLSERVER_SERVER=SERVER2016\SQL2017
SQLSERVER_DATABASE=Exir_sg3
SQLSERVER_USERNAME=Ai
SQLSERVER_PASSWORD=رمز_محلی_دیتابیس

OPENAI_API_KEY=کلید_شخصی_OpenAI
OPENAI_MODEL=gpt-5.6-luna
TREASURY_AGENT_MAX_TURNS=6
TREASURY_AGENT_SESSION_DB=./treasury_agent_sessions.db
```

فایل `.env` در `.gitignore` است. کلید OpenAI و رمز دیتابیس را در کد، پیام‌رسان یا
فایل ZIP قرار ندهید.

## 3. اجرای سرور

```bat
uvicorn app.main:app --reload
```

سپس Swagger را باز کنید:

```text
http://127.0.0.1:8000/docs
```

## 4. تست آماده‌بودن بدون مصرف اعتبار

در Swagger مسیر زیر را اجرا کنید:

```text
GET /api/v1/treasury/chat/status
```

اگر `ready` برابر `true` بود، کلید از `.env` خوانده شده و Agent نیز بدون خطا
بارگذاری شده است. در `diagnostics` وضعیت کلید، نسخه SDK و import Agent نمایش داده
می‌شود. این تست هیچ درخواستی به OpenAI ارسال نمی‌کند.

## 5. اولین سؤال

مسیر زیر را اجرا کنید:

```text
POST /api/v1/treasury/chat
```

بدنه درخواست:

```json
{
  "message": "آخرین ۵ پرداخت تأییدشده را بگو"
}
```

پاسخ یک `session_id` می‌دهد. برای سؤال بعدی همان شناسه را برگردانید تا Agent
گفت‌وگوی قبلی را به خاطر داشته باشد:

```json
{
  "message": "جمع همین موارد چقدر است؟",
  "session_id": "شناسه‌ای که پاسخ قبلی برگرداند"
}
```

## 6. سناریوهای تست پیشنهادی

1. `مانده حساب آبرام چقدر است؟`
2. در صورت چند حساب: انتخاب یکی از `account_id`های پیشنهادی در پیام بعدی.
3. `آخرین ۵ گردش همان حساب را نشان بده.`
4. `چک‌های صادرشده تا ۶۰ روز آینده را بگو.`
5. `چک‌های دریافتی برگشتی را نشان بده.`

Agent فقط ابزارهای از پیش تعریف‌شده خزانه را اجرا می‌کند و SQL آزاد تولید نمی‌کند.
هر پاسخ مالی باید بر داده برگشتی همین ابزارها متکی باشد.

## 7. مغایرت‌گیری صورتحساب بانک

در Swagger مسیر زیر را باز کنید:

```text
POST /api/v1/treasury/reconciliation/upload
```

فایل `CSV`، `XLSX` یا `XLS` را وارد کنید. `bank_account_id` از جدول
`RPA3.BankAccount` اختیاری است؛ اگر خالی باشد، سرویس با شماره حساب یا شبای
داخل فایل حساب بانکی را پیدا و در صورت وجود رکورد تکراری، رکورد دارای بیشترین
سابقه استفاده را انتخاب می‌کند. ستون‌های
تاریخ، واریز و برداشت الزامی‌اند. ستون‌های شرح، شماره پیگیری، مانده، نام
واریزکننده و حساب مبدأ اختیاری‌اند و در صورت متفاوت‌بودن نام عنوان‌ها می‌توان
نام دقیق هر ستون را در فرم Swagger وارد کرد.

`header_row=0` یعنی ردیف عنوان خودکار تشخیص داده شود. برای فایل واقعی
«بانک سپه فراز.xls»، شیت «صورت‌حساب» و ردیف عنوان ۸ خودکار شناسایی می‌شوند و
ردیف «مجموع» انتهای گزارش نیز وارد تطبیق نمی‌شود.
در خروجی XLSX بانک تجارت، ردیف عنوان ۱۸ شناسایی می‌شود. شماره حساب این بانک
زیر عنوان «شماره حساب» در ردیف بعدی قرار دارد و علاوه بر سربرگ، از ستون تکراری
شماره حساب در جزئیات نیز قابل استخراج است. ستون‌های `RRN`، «شرح تراکنش»،
«شرح سند» و «شماره سند» نیز برای افزایش کیفیت تطبیق خوانده می‌شوند.
نام بانک از نام فایل و Sheet تشخیص داده می‌شود و شبای خود حساب از حواله‌ای
استخراج می‌شود که انتهای شبای مقصد با شماره حساب فایل برابر باشد. بنابراین اگر
شماره مشابهی در بانک دیگری وجود داشته باشد، حساب آن بانک به اشتباه انتخاب
نمی‌شود.
شماره حساب بانک تجارت در فایل به‌صورت `010 + شماره ۹ رقمی راهکاران + رقم
کنترل` است. برای نمونه `0103560567794` به حساب `356056779` و
`0103560567877` به حساب `356056787` در `RPA3.BankAccount` نگاشت می‌شود.

برای فایل «بانک سپه فراز.xls»، شناسه حساب بانکی تأییدشده `82` است. واریزهای
بانک با آیتم‌های تأییدشده `RPA3.ReceiptDeposit` و برداشت‌ها با آیتم‌های
`RPA3.PaymentDeposit` مقایسه می‌شوند. `AccountRef` این آیتم‌ها حساب طرف مقابل
است و نباید به‌عنوان حساب بانکی انتخاب شود.
انتقال‌های بین حساب‌های خود شرکت از `RPA3.TransferDeposit` خوانده می‌شوند؛
فقط هدرهای `RPA3.Transfer` با `State=3` معتبرند. اگر حساب جاری مقصد انتقال
باشد مبلغ دریافتی به‌عنوان واریز، و اگر مبدأ باشد مبلغ پرداختی به‌عنوان برداشت
تشخیص داده می‌شود. طبق تصمیم واحد خزانه، انتقال بین تمام حساب‌های متعلق به
شرکت—even اگر دو بانک متفاوت باشند—با دلیل `internal_transfer_policy` در وضعیت
مستقل «انتقال داخلی شرکت» قرار می‌گیرد و در تعداد، مبلغ و درصد «بدون سند» وارد
نمی‌شود.
در خلاصه گزارش، «نرخ تعیین تکلیف قطعی» علاوه بر سندهای قطعی و گردش‌های
خنثی‌شده، انتقال داخلی شناسایی‌شده را نیز پوشش می‌دهد؛ این شاخص با نرخ
«سندخورده» متفاوت است.

خروجی پنج وضعیت کسب‌وکاری دارد:

- `posted`: سند متناظر یکتا پیدا شده است.
- `reversed`: برداشت و برگشت بانکی همدیگر را خنثی کرده‌اند.
- `internal_transfer`: انتقال بین حساب‌های متعلق به خود شرکت است.
- `needs_review`: تطبیق احتمالی، اختلاف مبلغ، کاندید مبهم یا ردیف تکراری است.
- `unposted`: سند پیشنهادی قابل اتکا پیدا نشده است.

برای برداشت‌های بانکی دارای عبارت «کارمزد»، یک قاعده تجمیعی اجرا می‌شود:
کارمزدهای یک روز با هم جمع می‌شوند و فقط وقتی مجموع آن‌ها دقیقاً با یک سند
کارمزد همان روز در راهکاران برابر باشد، با روش `daily_fee_group` سندخورده اعلام
می‌شوند. وجود چند سند با جمع یکسان، نتیجه را «نیازمند بررسی» نگه می‌دارد.
برداشت و برگشت‌های هم‌تاریخ و هم‌مبلغ ابتدا جفت می‌شوند؛ سپس مبلغ خالص
کارمزدهای باقی‌مانده با سند روزانه راهکاران مقایسه می‌شود. عبارت‌های مشخص
هزینه بانکی مانند «هزینه حسابرسی» و «دستور پرداخت سمت متعهد» نیز فقط بر اساس
شرح تراکنش، نه صرفاً کوچک‌بودن مبلغ، وارد گروه کارمزد می‌شوند.
در خروجی بانک سپه ممکن است ابتدای شرح «برگشت عملیات» و انتهای آن «بازگشت
عملیات» درج شده باشد. هر دو نشانه حذف می‌شوند و اگر تعداد، تاریخ و مبالغ دو
طرف برابر باشد، گروه تکراری به‌صورت قطعی «برگشت یا خنثی‌شده» گزارش می‌شود.
اگر یک کارمزد سند مستقل داشته باشد و بقیه کارمزدهای همان روز در یک سند تجمیعی
ثبت شده باشند، سیستم ابتدا جفت مبلغ یکتای مستقل را جدا می‌کند و سپس مجموع
باقی‌مانده را دوباره با سند تجمیعی می‌سنجد.

اگر در یک روز چند گردش هم‌مبلغ و چند ردیف هم‌مبلغ در راهکاران وجود داشته باشد،
سیستم آن‌ها را به‌صورت گروهی بررسی می‌کند. فقط وقتی تعداد و مجموعه مبالغ دو طرف
برابر باشد و هر ردیف راهکاران دقیقاً یک‌بار مصرف شود، گروه سندخورده اعلام
می‌شود. گروه متوازن داخل بازه مجاز تاریخ نیز با همین شرط قابل تطبیق است.
انتقال وجهی که فقط از نظر مبلغ و تاریخ به رویداد وصول چک شبیه باشد، خودکار
سندخورده نمی‌شود و برای تأیید خزانه در `needs_review` قرار می‌گیرد.
تلورانس عمومی تاریخ دو روز است؛ اما اگر سریال چک دقیقاً در اطلاعات راهکاران
پیدا شود، فاصله ثبت تا ۴۵ روز پذیرفته می‌شود. این استثنا برای نمونه‌های واقعی
بانک تجارت لازم است که تغییر وضعیت بعضی چک‌ها تا ۳۷ روز بعد ثبت شده است.
برابری مبلغ بدون سریال یا شناسه معتبر برای استفاده از این بازه طولانی کافی
نیست.

پاسخ آپلود یک `reconciliation_id` می‌دهد. شناسه را می‌توان در Chat به Agent داد،
مثلاً: «خلاصه مغایرت‌گیری با شناسه ... را بگو» یا «ردیف‌های بدون سند همین گزارش
را نشان بده». همچنین گزارش مستقیماً از این مسیرها قابل دریافت است:

```text
GET /api/v1/treasury/reconciliation/{reconciliation_id}
GET /api/v1/treasury/reconciliation/{reconciliation_id}/summary
GET /api/v1/treasury/reconciliation/{reconciliation_id}/rows?business_status=internal_transfer
GET /api/v1/treasury/reconciliation/{reconciliation_id}/rows?business_status=unposted
GET /api/v1/treasury/reconciliation/{reconciliation_id}/export.xlsx
```

مسیر `export.xlsx` یک فایل آماده بررسی واحد خزانه می‌سازد که شامل شیت‌های
«خلاصه»، «سندخورده»، «برگشت یا خنثی‌شده»، «انتقال داخلی شرکت»،
«نیازمند بررسی»، «بدون سند احتمالی»
و «اسناد تطبیق‌قطعی‌نشده» است. شیت آخر الزاماً به معنی نبود گردش بانک نیست؛
بلکه اسناد راهکارانی را نشان می‌دهد که هنوز در یک تطبیق قطعی مصرف نشده‌اند.
در هر ردیف، اطلاعات گردش بانک و در صورت وجود، شماره و مشخصات سند متناظر
راهکاران کنار هم قرار می‌گیرند. شیت خلاصه نام بانک، شماره حساب شرکت، شماره شبا
و مشخصات شعبه را مستقیماً از اطلاعات بانکی راهکاران نمایش می‌دهد. همچنین برای
هر وضعیت، تعداد و مبلغ واریزها و برداشت‌ها را جداگانه نشان می‌دهد؛ بنابراین
مبلغ «بدون سند» به تفکیک واریز و برداشت مشخص است.
در شیت خلاصه سه شاخص جدا نمایش داده می‌شود: «نرخ تطبیق قطعی»، «پوشش قطعی با
احتساب برگشت» و «پوشش با تلورانس و موارد احتمالی». شاخص سوم برای برآورد نزدیک
به واقعیت است و موارد نیازمند بررسی را با سند قطعی مخلوط نمی‌کند.

شماره حساب از عبارت‌هایی مانند «صورت‌حساب سپرده» یا «شماره حساب» در سربرگ،
سلول زیر عنوان، یا ستون شماره حساب جزئیات استخراج می‌شود. عنوان
گزارش با چهار رقم آخر همان شماره و نام بانک ساخته می‌شود؛ برای نمونه شماره
`3101065266475` به‌صورت «حساب 6475 بانک سپه» نمایش داده می‌شود. شماره کامل حساب
و شبا نیز جداگانه در شیت خلاصه باقی می‌مانند.

فایل اصلی بانک ذخیره نمی‌شود؛ فقط نتیجه تجزیه و تطبیق در فایل محلی
`treasury_reconciliation.db` نگه‌داری می‌شود. نتیجه `needs_review` هیچ‌گاه به‌صورت
خودکار سندخورده اعلام نمی‌شود.

## تسویه چندچکی مشتری و چک شخص ثالث

نام صاحب حساب درج‌شده روی چک الزاماً بدهکار شرکت نیست. برای نمونه ممکن است
«صابری» چند چک متعلق به اشخاص دیگر را بابت بدهی خودش تحویل دهد. تخصیص چک به
بدهکار فقط از ارتباط صریح راهکاران انجام می‌شود: ابتدا
`RPA3.ReceiptReceivableNote.CounterPartRef` و در نبود آن
`RPA3.Receipt.CounterPartRef`. متن `AccountNumber` فقط برای نمایش صاحب/حساب چک
است و هیچ‌گاه مبنای تخصیص خودکار قرار نمی‌گیرد.

ابتدا بدهکار دارای چک را جست‌وجو کنید:

```text
GET /api/v1/treasury/cheques/received/debtors/search?name=صابری
```

سپس `counterpart_ref` نتیجه را برای گزارش تسویه بفرستید:

```text
GET /api/v1/treasury/cheques/received/settlement?counterpart_ref=900001
```

اگر مبلغ بدهی ابتدای محاسبه معلوم است، آن را نیز ارسال کنید:

```text
GET /api/v1/treasury/cheques/received/settlement?counterpart_ref=900001&opening_debt=1000000000
```

گزارش دو مانده جدا دارد:

- مانده قطعی: فقط چک‌های وصول‌شده از بدهی کم می‌شوند.
- مانده موقت: چک‌های وصول‌شده و در جریان وصول از بدهی کم می‌شوند.

چک واخواست‌شده از هر دو محاسبه حذف می‌شود. فیلد `third_party_indicator` فقط
نشان می‌دهد نام بدهکار در متن حساب چک دیده نشده است؛ حتی در این حالت تخصیص
براساس `CounterPartRef` صریح راهکاران قطعی باقی می‌ماند.

## قابلیت‌های هوشمند مدیریتی خزانه

قابلیت‌های زیر به همان Treasury Agent اضافه شده‌اند و هرکدام Endpoint مستقل
برای تست در Swagger دارند:

```text
GET /api/v1/treasury/overview/daily?due_days=7
GET /api/v1/treasury/risk/cheques?days=60
GET /api/v1/treasury/controls/anomalies?days=30
GET /api/v1/treasury/planning/payments?days=30&available_cash=50000000000
GET /api/v1/treasury/customers/{counterpart_ref}/profile?days=90
GET /api/v1/treasury/dashboard/executive?days=30
```

- گزارش روزانه، جمع اسناد دریافت و پرداخت امروز و هشدار سررسید را نمایش
  می‌دهد. `document_net_movement` مانده بانک نیست و فقط خالص اسناد تأییدشده
  همان روز است.
- داشبورد ریسک، چک‌های آتی، معوق، واخواست‌شده و تمرکز مبلغ روی طرف حساب‌ها را
  گزارش می‌کند. درصد پوشش فقط مقایسه اسمی چک‌های دریافتی و صادرشده است و تضمین
  وصول نیست.
- گزارش معوق فقط چک‌های عادی (`NormalORGuarantee=1`) در بازه گذشته انتخابی را
  در هشدار عملیاتی وارد می‌کند؛ سوابق بسیار قدیمی و چک تضمینی به‌عنوان هشدار
  روز جاری نمایش داده نمی‌شوند. `total_count` و `total_amount` عدد کامل‌اند و
  `returned_count` فقط تعداد ردیف‌های جزئیات نمایشی است.
- تمرکز طرف حساب در داشبورد ریسک با Query تجمیعی مستقل روی تمام چک‌های آتی
  محاسبه می‌شود و به سقف ردیف‌های جزئیات وابسته نیست. `overdue_scope` بازه
  معوق‌ها را مشخص می‌کند؛ `protested_scope=current_state_all_history` یعنی مبلغ
  واخواست مربوط به کل سوابقی است که هنوز همین وضعیت را دارند، نه فقط بازه آینده.
- کنترل موارد غیرعادی، اسناد احتمالاً تکراری، مبلغ‌های بزرگ و سندهای بدون شرح
  را با قاعده و مدرک نمایش می‌دهد. این خروجی اثبات تخلف نیست.
- برنامه پرداخت، چک‌های صادرشده را بر اساس سررسید اولویت‌بندی و در صورت دریافت
  `available_cash` کسری منابع را محاسبه می‌کند؛ هیچ پرداختی اجرا نمی‌شود.
- پرونده مشتری، حساب‌ها، گردش دوره و چک‌های تخصیص‌یافته به طرف حساب را کنار هم
  قرار می‌دهد. تا زمان اتصال جداول فروش، فاکتورهای باز در آن محاسبه نمی‌شوند.
- داشبورد مدیریتی خروجی چهار گزارش روزانه، ریسک چک، برنامه پرداخت و کنترل
  موارد غیرعادی را یکجا برای ارائه برمی‌گرداند.

نمونه سؤال‌های Chat:

```text
امروز وضعیت خزانه چطور است؟
تا ۶۰ روز آینده چه ریسک چکی داریم؟
پرداخت‌های غیرعادی ۳۰ روز اخیر را نشان بده.
با ۵۰ میلیارد ریال موجودی، برنامه پرداخت ۳۰ روز آینده چیست؟
پرونده مالی طرف حساب 904420 را توضیح بده.
یک گزارش جامع برای مدیر خزانه بساز.
```

## 8. تست‌های قطعی

```bat
python -m unittest test_financial_calculation.py -v
python -m unittest test_bank_reconciliation.py -v

```

این تست‌ها درصد، جمع، میانگین، گردکردن و خطای تقسیم بر صفر را بدون اتصال به
SQL Server یا مصرف اعتبار OpenAI بررسی می‌کنند. برای نمونه، درصد مبلغ
`2,150,000,000` از `3,795,890,000` باید `56.64` برگردد.

تاریخ‌های خزانه در خروجی Service هم به شکل میلادی و هم در فیلدهای پایان‌یافته
با `_jalali` تولید می‌شوند. Agent موظف است تاریخ شمسی را نمایش دهد. نام ارز فقط
زمانی نمایش داده می‌شود که در خروجی Tool مشخص باشد و از روی `CurrencyRef` حدس
زده نمی‌شود.
# مسیر ساده کارمند خزانه

برای استفاده روزمره فقط Endpoint زیر را باز کنید:

```text
POST /api/v1/treasury/reconciliation/auto-upload
```

کارمند فقط فایل XLS، XLSX یا CSV بانک را انتخاب می‌کند. شماره حساب، شبا، بانک،
Sheet، ردیف عنوان، ستون‌ها و فاصله مجاز تاریخ به‌صورت خودکار تعیین می‌شوند.
Endpoint قدیمی `/reconciliation/upload` فقط برای پشتیبانی فنی و تنظیم دستی است.
